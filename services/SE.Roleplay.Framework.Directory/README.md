# SE Roleplay Framework Directory Service

A self-hosted directory API for the **Space Engineers 1** launcher. It publishes community server listings and accepts authenticated heartbeat updates from registered servers.

## Run

Requires the .NET 8 SDK/runtime.

Set these environment variables before starting:

- SERPF_DIRECTORY_ADMIN_KEY — a long, random secret used for registration/deletion.
- SERPF_DIRECTORY_AUTH_DB_PATH — optional path for the shared SQLite database (authentication and server listings).
- SERPF_DIRECTORY_DATA_PATH — optional path to an existing legacy JSON data file; it is imported once and then left untouched.

Run:

    dotnet run --project services/SE.Roleplay.Framework.Directory

Host this service behind an HTTPS reverse proxy in production. Never expose the admin key in a launcher build or commit it to source control.

## Endpoints

- GET /health — health check.
- GET /api/servers — public server feed. The response uses the launcher's { "servers": [...] } format.
- POST /api/admin/servers — register a server. Requires X-Directory-Admin-Key.
- PUT /api/servers/{id}/heartbeat — update player count/version. Requires X-Server-Api-Key.
- DELETE /api/admin/servers/{id} — remove a listing. Requires X-Directory-Admin-Key.

## Register a server

POST /api/admin/servers with the X-Directory-Admin-Key header and JSON body:

    {
      "name": "Example RP Community",
      "description": "Persistent SE1 roleplay",
      "address": "play.example.net",
      "port": 27016,
      "maxPlayers": 32,
      "region": "North America",
      "websiteUrl": "https://example.net",
      "discordUrl": "https://discord.gg/example",
      "rulesUrl": "https://example.net/rules",
      "tags": ["roleplay", "survival"]
    }

The response contains a generated server ID and a random API key. Save that key securely; it is returned only during registration. Only its SHA-256 hash is persisted by the directory.

## Send a heartbeat

PUT /api/servers/SERVER_ID/heartbeat with the X-Server-Api-Key header and JSON body:

    { "players": 4, "maxPlayers": 32, "version": "SE1 server version" }

Listings become Offline when no heartbeat has been received for 90 seconds. A Torch heartbeat sender is a follow-up integration; this API can first be exercised with a small server-side agent or manual HTTP request.

## Security notes

- Configure a unique, high-entropy admin key using the environment variable.
- Put the service behind HTTPS; never send API keys over plaintext remote HTTP.
- Server API keys are generated cryptographically, stored as SHA-256 hashes, and compared using fixed-time verification.
- The public feed never includes credential hashes.
- Server listings, owner associations, and API-key hashes are stored in the shared SQLite database. Each mutation is a database statement or transaction, so independent service instances do not overwrite one another's updates.
- On first startup after this migration, an existing file at `SERPF_DIRECTORY_DATA_PATH` (or `Directory:DataPath`) is imported once per database and source path. The source JSON is retained as a backup and is not modified. Malformed legacy JSON stops startup rather than silently discarding listings; fix or restore the file before restarting.
- Set `SERPF_DIRECTORY_AUTH_DB_PATH` to the same durable shared database location for all service instances. SQLite should be placed on storage with reliable local filesystem locking; do not assume arbitrary network filesystems are safe for SQLite WAL.

## Steam login state groundwork

The service registers an internal `SteamLoginStateStore` for owner sign-in. It creates 256-bit cryptographically random URL-safe state values, stores only SHA-256 digests, binds each state to a server-generated browser-session identifier, and allows one successful consume within a maximum five-minute lifetime. SQLite-backed consumption is atomic across service instances.

The login and callback endpoints now use this store. Browser-session identifiers are generated by the server, issued only in a Secure, HttpOnly, SameSite=Lax cookie, and never accepted from request parameters or a request body. The store is backed by the shared SQLite authentication database; state hashes and browser-session hashes are persisted, and a conditional DELETE ... RETURNING statement ensures only one instance can consume a valid state.

## Steam browser sign-in groundwork

Set `SERPF_DIRECTORY_PUBLIC_BASE_URL` (or `Directory:PublicBaseUrl`) to the directory's public HTTPS origin, for example `https://directory.example/`. It must be an origin root with no path, query, or fragment. The service exposes:

- GET `/auth/steam/login` — creates a short-lived state bound to a server-generated browser cookie, then redirects to Steam OpenID.
- GET `/auth/steam/callback` — consumes the state, validates the signed assertion directly with Steam, and issues a protected owner-session cookie containing the verified SteamID64.

The browser-binding cookie is `Secure`, `HttpOnly`, `SameSite=Lax`, and uses the `__Host-` prefix. The authenticated session uses an ASP.NET Core protected cookie with a 12-hour sliding lifetime. Login and callback requests share a per-IP fixed-window rate limit. Data Protection keys are persisted outside the application directory using `SERPF_DATA_PROTECTION_KEYS_PATH` (or `Directory:DataProtectionKeysPath`); the default is the service account's `.aspnet/Data-Protection-Keys/SE-Roleplay-Framework` directory. Protect this directory with operating-system permissions and back it up securely.

When deployed behind a reverse proxy, configure forwarding only for explicitly trusted proxy addresses/networks and ensure the public endpoint enforces HTTPS. Do not trust arbitrary forwarded headers. Keep the public URL stable and identical to the HTTPS origin used for Steam callbacks.

This milestone establishes sign-in only. It does not add owner registration, listing-management routes, or an owner UI. The existing bootstrap-admin routes remain separate and must not be exposed through launcher configuration. Steam login state, desktop OAuth authorization state/code, launcher access/refresh token storage, and Steam OpenID nonce replay protection are shared through SQLite. Steam nonce values are SHA-256 hashed and inserted atomically only after Steam confirms the assertion; duplicate assertions are rejected across service instances.


## Shared authentication database foundation

The service now initializes a SQLite database at startup. Configure its location with `SERPF_DIRECTORY_AUTH_DB_PATH` or `Directory:AuthDatabasePath`; the default is `data/directory-auth.db` under the application base directory. The database uses WAL journaling, full synchronous durability, foreign-key enforcement, and a 10-second busy timeout.

Schema version 2 includes tables for Steam login states and nonce replay records, desktop authorization states and codes, token families, access tokens, and refresh tokens. Version 2 adds the shared Steam OpenID nonce replay table to existing version 1 installations. OAuth state, browser-session, authorization-code, access-token, refresh-token, and Steam nonce values are stored only as SHA-256 hashes; expiry and family indexes support cleanup and revocation.

**Important:** SQLite now backs Steam login states, desktop OAuth authorization states/codes, and launcher access/refresh tokens. Refresh-token rotation is atomic across instances; replay of a consumed refresh token revokes the entire token family, including access tokens. The server directory JSON store remains process-local/single-instance. The directory service as a whole is not yet safe for multi-instance deployment.


## SQLite server directory storage

Schema version 3 adds the `directory_servers` table and indexes for owner and public-name queries. It also adds `directory_server_imports`, which records one-time legacy imports. The existing `Directory:AuthDatabasePath` / `SERPF_DIRECTORY_AUTH_DB_PATH` setting is the single database location for login/OAuth security state and server listings.

The service initializes the database and imports the configured legacy JSON file before accepting requests. Imports preserve server IDs, ownership, heartbeat values, tags, and API-key hashes; duplicate IDs already present in SQLite are left unchanged. A failed import rolls back its import marker and inserted rows together, so startup can be safely retried. The JSON file is never deleted or rewritten.

All directory operations now use SQLite: public and owner reads, registration, owner-scoped updates/deletes, API-key rotation, heartbeats, and administrative deletion. API-key hashes remain SHA-256 digests and are checked with fixed-time comparison. Owner checks are enforced in the SQL mutation predicates, not by trusting client-supplied owner IDs.


## Persistent player profiles and server permissions

Schema version 4 adds durable player profiles and server-scoped permission grants.

- `GET /api/player/profile` and `PUT /api/player/profile` use the launcher's validated bearer token. The SteamID64 is taken only from the token; clients cannot select another player's identity.
- Player profiles store a display name (up to 40 characters) and biography (up to 500 characters). A profile is private to its authenticated player unless a future public-profile endpoint is explicitly added.
- `GET /api/servers/{serverId}/permissions/me` returns the signed-in player's active permissions for that server only.
- Server owners can grant permissions with `POST /api/owner/servers/{serverId}/players/permissions` and revoke them with `DELETE` on the same route. These browser-cookie mutations require the existing same-origin and antiforgery protections.
- Grants are keyed by server, player SteamID64, and permission name. Permission names are lowercase keys using letters, digits, dots, underscores, hyphens, and colons. Optional expiry is limited to 365 days.
- Grant and revoke SQL statements verify server ownership in the same statement as the mutation. A server deletion cascades its grants. Expired grants are never returned as active.
- Player profile and permission data are stored in the shared SQLite database, so they persist across restarts and service instances using the same database.
